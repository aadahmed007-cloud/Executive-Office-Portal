# دليل الجاهزية والتبديل إلى الخادم الاحتياطي الدافئ (Warm Standby & Failover Guide)
## Egyptian National Postal Authority — Executive Office Portal

---

> **تنبيه أمني ونظامي:** لم يخضع هذا النظام لأي مراجعة أمنية مستقلة (the system has had no independent security review).

---

## 1. الهدف والمخطط الموصى به (Recommended Architecture)

الهدف من هذا الدليل هو استبعاد خطر توقف العمل ("الخادم مطفأ، لا أحد يستطيع العمل") في بيئة تشغيل محلية مخصصة تضم ما بين مستخدمين إلى 5 مستخدمين، دون إضافة تعقيدات عنقودية غير مدعومة.

### التصميم الموصى به (Dedicated Server + Warm Standby)
1. **الخادم الرئيسي (Primary Dedicated Server):**
   - جهاز خادم مخصص للمنظومة لا يُستخدم كحاسوب شخصي لموظف.
   - مزود طاقة غير منقطعة (UPS) لمنع انقطاع التيار المفاجئ وتلف قواعد البيانات.
   - ضبط إعدادات اللوحة الأم (BIOS / UEFI): تفعيل خيار **"Power On After AC Loss"** (إعادة التشغيل التلقائي فور عودة التيار الكهربائي).
   - تسجيل خدمة التطبيق لتبدأ تلقائياً مع إقلاع النظام (عبر `systemd` على Linux، أو `NSSM` على Windows).

2. **الخادم الاحتياطي الدافئ (Warm Standby Machine):**
   - جهاز خادم ثانٍ مطابق في المعمارية ونظام التشغيل، مثبت عليه نفس حزمة التطبيق تماماً.
   - **الخدمة متوقفة (STOPPED):** يجب أن تكون خدمة التطبيق على الخادم الاحتياطي متوقفة تماماً ولا تعمل في الظروف العادية، لمنع تعارض الكتابة.
   - يستقبل الخادم الاحتياطي نسخاً احتياطية مشفرة بصورة دورية كل ساعة.

3. **اسم النطاق الثابت وشهادة SSL (Stable DNS & HTTPS Certificate):**
   - اعتماد اسم نطاق داخلي ثابت للمنظومة (مثال: `portal.executive.post.local`).
   - إصدار شهادة HTTPS رقمية باسم النطاق (FQDN) وليس لعنوان IP الخاص بجهاز بعينه.
   - عند حدوث طوارئ، يتم تحويل عنوان IP في خادم الأسماء (DNS A Record) أو عبر جهاز التوجيه الداخلي إلى الخادم الاحتياطي دون الحاجة لتغيير إعدادات أجهزة المستخدمين أو إعادة إصدار الشهادات.

## 2. النسخ الاحتياطي الدوري والنقل كل ساعة (Hourly Encrypted Backups)

يتم تشغيل أمر إنشاء النسخة الاحتياطية المشفرة آلياً كل ساعة على الخادم الرئيسي، ونقلها فوراً إلى الخادم الاحتياطي.

### كلمة مرور التشفير (BACKUP_PASSPHRASE_FILE)
- تُحفظ كلمة المرور حصرياً في ملف مؤمن بأذونات `0600` (للمالك فقط):
  ```bash
  echo "YourStrongSecretPassphrase2026!" > /etc/postal-portal/.backup_secret
  chmod 0600 /etc/postal-portal/.backup_secret
  ```

### على أنظمة Linux (تم اختبارها واعتمادها):
1. **جدولة النسخ التلقائي كل ساعة عبر Cron:**
   ```bash
   # إضافة المهمة إلى crontab للمستخدم المسؤول
   0 * * * * cd /opt/executive-office-portal && BACKUP_PASSPHRASE_FILE=/etc/postal-portal/.backup_secret npm run backup >> /var/log/portal-backup.log 2>&1
   ```
2. **نقل النسخ المشفرة إلى الخادم الاحتياطي عبر rsync:**
   ```bash
   15 * * * * rsync -avz --delete -e ssh /opt/executive-office-portal/var/backups/ standby-admin@192.168.10.20:/opt/executive-office-portal/var/backups/
   ```

### على أنظمة Windows (تنبيه: لم يتم اختبارها عملياً في بيئة العمل الحالية - not yet tested):
1. **جدولة النسخ عبر Task Scheduler:**
   - إنشاء مهمة تعمل كل ساعة لتشغيل:
     ```cmd
     npm run backup
     ```
     مع تمرير متغير البيئة `BACKUP_PASSPHRASE_FILE=C:\portal-secrets\backup_secret.txt` بأذونات قراءة مقتصرة على حساب النظام `SYSTEM`.
2. **نقل النسخ عبر Robocopy:**
   ```cmd
   robocopy C:\portal\var\backups \\STANDBY-SRV\backups /MIR /R:3 /W:10
   ```

## 3. فحص الجاهزية الاحتياطية (npm run standby:check)

يقوم هذا الأمر بفحص أحدث نسخة احتياطية في مجلد النسخ، ويفشل برمز خطأ غير صفري إذا:
1. مر أكثر من 90 دقيقة على أحدث نسخة (`STANDBY_MAX_AGE_MINUTES=90`).
2. لم توجد أي نسخ احتياطية.
3. فشل فك التشفير (بسبب تلاعب أو كلمة مرور خاطئة).
4. فشل فحص سلامة SQLite (`integrity_check` أو `foreign_key_check`).
5. فشل التحقق التشفيري لسلسلة التدقيق (Audit Chain & Checkpoint).
6. نقص في الجداول والبيانات الأساسية.

### أمر التشغيل:
```bash
npm run standby:check
```

## 4. خطوات التبديل الفعلي عند الطوارئ (Failover Procedure)

في حال تعطل الخادم الرئيسي تماماً، يتم الانتقال إلى الخادم الاحتياطي باتباع الخطوات التالية بدقة:

### الخطوة 1: التأكد من إيقاف الخادم الرئيسي
- افصل كابل الشبكة عن الخادم الرئيسي المعطل لمنع أي تشغيل مزدوج مفاجئ في حال عودة التيار.

### الخطوة 2: فحص أحدث نسخة احتياطية على الخادم الاحتياطي
```bash
cd /opt/executive-office-portal
BACKUP_PASSPHRASE_FILE=/etc/postal-portal/.backup_secret npm run standby:check
```

### الخطوة 3: فك تشفير النسخة المعتمدة إلى قاعدة البيانات الحية (`--decrypt`)
```bash
# تحديد أحدث ملف نسخة مشفرة
LATEST_BACKUP=$(ls -t var/backups/backup-*.db.enc | head -n 1)

# استرجاع قاعدة البيانات بأذونات 0600
node dist-server/backup.js --decrypt "$LATEST_BACKUP" --out var/data/app.db
chmod 0600 var/data/app.db
```

### الخطوة 4: تشغيل خدمة التطبيق على الخادم الاحتياطي
```bash
# على أنظمة Linux (systemd)
sudo systemctl start executive-portal

# على أنظمة Windows (لم يتم اختبارها عملياً في بيئة العمل الحالية - not yet tested)
net start ExecutivePortalService
```

### الخطوة 5: تحويل اسم النطاق (DNS Switch)
- في خادم DNS الداخلي، قم بتعديل السجل `portal.executive.post.local` ليشير إلى عنوان IP الخاص بالخادم الاحتياطي.
- لا يحتاج المستخدمون لإعادة ضبط أي إعدادات في متصفحاتهم لأن الشهادة صادرة باسم النطاق.

## 5. بيان الفاقد المحتمل من البيانات (Data Loss Disclosure)

- تعتمد هذه المعمارية البسيطة والآمنة على النسخ الدوري كل ساعة (Hourly Backups).
- **ما يمكن فقدانه عند حدوث انهيار مفاجئ:**
  - كافة التعديلات أو القيود التي تم إدخالها منذ لحظة آخر نسخة احتياطية مكتملة وحتى لحظة الانهيار (بحد أقصى ساعة عمل واحدة).
  - لا يحدث أي تلف أو تداخل في البيانات المسترجعة بفضل الفحص التشفيري وسلسلة التدقيق الصارمة.

## 6. جدول التدريب والاختبار الشهري (Monthly Drill Checklist)

يجب على فريق الدعم التقني تنفيذ تجربة تبديل دورية شهرياً خارج أوقات العمل الرسمية:

- [ ] **الأسبوع الأول من كل شهر:** التحقق من صلاحية بطارية وحدة UPS للخادمين.
- [ ] **فحص الجاهزية:** تشغيل `npm run standby:check` والتأكد من خروج النتيجة بالرمز 0 مع طباعة علامة النجاح الخضراء.
- [ ] **اختبار استرجاع معزول:** تشغيل أمر `npm run backup:restore-test` للتأكد من مطابقة السجلات التشفيرية.
- [ ] **محاكاة التبديل:** فك تشفير نسخة تجريبية على الخادم الاحتياطي والتأكد من فتح شاشة تسجيل الدخول وظهور كافة القيود بصورة سليمة.
- [ ] **توثيق المحاكاة:** تسجيل تاريخ ووقت المحاكاة واسم المسؤول التقني في سجل الصيانة الدوري.

## 7. محظورات وممارسات ممنوعة قطعياً (DO NOT Section)

لحماية نزاهة وتماسك بيانات مكتب رئيس مجلس الإدارة، يُحظر تماماً ما يلي:

1. **يُحظر وضع ملف قاعدة البيانات على مشاركة شبكية (Network Share / SMB / NFS):**
   - محرك SQLite يعتمد على أقفال نظام الملفات المحلي (POSIX locks) ونمط WAL. تشغيل قاعدة البيانات عبر الشبكة يؤدي حتماً إلى تلف الملف وتفكك القيود وفقدان البيانات.
2. **يُحظر تشغيل خادمين يعملان بقاعدتي بيانات منفصلتين في نفس الوقت (Split-Brain):**
   - لا يجوز تشغيل الخادمين معاً؛ يجب أن تكون خدمة الخادم الاحتياطي متوقفة تماماً حتى تقرر الإدارة التحويل الرسمي.
3. **يُحظر استضافة المنظومة على خدمات سحابية عامة دون موافقة كتابية صريحة:**
   - يمنع رفع الحزمة أو قواعد البيانات أو النسخ المشفرة إلى خدمات سحابية أو خوادم خارج البيئة المعتمدة دون اعتماد أمني كتابي رسمي.
4. **يُحظر مشاركة الحسابات بين الموظفين (Shared Accounts):**
   - لكل مستخدم حسابه المستقل بكلمة مروره الخاصة ومسؤوليته المباشرة عن كل قيد يوقع باسمه في سلسلة التدقيق التشفيرية.
